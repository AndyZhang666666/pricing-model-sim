# Pricing Model Sim

给一条留存曲线和几个定价参数，算出「单次解锁 / 包月订阅 / 混合」三种付费机制 12 个月的 ARPU、LTV、回本周期，并回答一个问题：**你的业务该选哪种**。

拖一条留存曲线 → 调几个价格参数 → 看三条线谁高谁低、在哪个参数上换手。全部计算在浏览器里完成，没有服务端。

- **在线 Demo**：https://andyzhang666666.github.io/pricing-model-sim/
- **姊妹项目**：[creative-eval](https://github.com/AndyZhang666666/creative-eval)（长文本评测台）、[filing-eval](https://github.com/AndyZhang666666/filing-eval)（公告事实核查裁判）

## 它解决什么问题

收入下滑的时候，团队的第一反应往往是加大买量。但问题未必在获客，也可能在**付费机制**——我做海外短剧付费时就遇到过这种情况：包月订阅市场的复购率比单集解锁市场高三倍多。

最花时间的不是分析，是**说服**。你得让所有人看见「同一批用户，换个付费机制，12 个月能差出多少收入」。Excel 能算一两组参数，但要扫一遍「月费 25 到 40、免费集数 0 到 15」，找出**最优机制在哪个值上换手**，手算就崩了。

这个工具就是把那张说服用的表做成能随便调参数的模拟器。目标用户是独立开发者、小型内容应用主，以及任何在「买断还是订阅」之间纠结的人。

## 怎么用

```bash
npm install
npm run dev          # 打开 http://localhost:3000/pricing-model-sim/
```

注意地址栏要带 `/pricing-model-sim/` 这一段：`next.config.mjs` 里设了 `basePath`（GitHub Pages 部署要求），所以本地开发时根路径 `/` 是空的，直接访问 `localhost:3000` 会 404。

四个页面：

| 页面 | 干什么 |
|---|---|
| **留存曲线** | 拖 D1/D7/D30/D90/D180 五个锚点，或选预设（短剧 / 工具 / 社交三类）。曲线实时重拟合 |
| **三机制对比**（核心） | 调参数 → 看三种机制的 LTV 对比、回本月份，以及一张**结论卡**告诉你谁更优、为什么 |
| **敏感性分析** | 选一个参数（月费 / 免费集数 / 订阅转化率 / 切换摩擦 / CAC / 付费率）扫一遍，找**最优机制的换手点** |
| **案例库** | 4 个合成案例，各带一组参数和一段点评，可一键载入模拟器继续调 |

跑校验脚本：

```bash
npm run check        # 依次跑手算校验 → 守恒检查 → 敏感性扫描
npm run test-model   # 只跑手算对照，输出 results/model-check.json
npm run sanity       # 只跑守恒检查，输出 results/sanity.json
npm run sweep        # 只跑敏感性扫描，输出 results/sweep.json
```

## 核心逻辑与假设

三种机制必须在**同一个刻度**上比较，否则比出来的东西没有意义。这个刻度是：

> `revUnit(k)` = 一个**新获取的用户**在自己生命周期第 k 个月贡献的收入（已扣平台抽成）

所有指标都从这一个序列长出来——**不是**从「当月总收入」出发，因为那会把不同月龄的用户混在一起：

```
第 m 月累计 ARPU = Σ_{k=1..m} revUnit(k)          ← 与 CAC 同轴，直接可比
12 月 LTV        = Σ_{k=1..12} revUnit(k) / (1+r)^(k-1)
回本月份          = 首个累计（折现）ARPU ≥ CAC 的月份
第 m 月总收入     = 当月新增用户数 × Σ_{k=1..m} revUnit(k)
第 m 月末存量     = 当月新增用户数 × Σ_{k=1..m} S_k
```

ARPU 的分母是**当月新增用户**，不是当月活跃存量。只有 cohort 口径的每用户收入才和 CAC 可比；除以活跃存量的那个是「单位存量变现效率」，也算了（`stockArpu`），但不用它算回本。

三种机制的收入口径：

```
单次解锁   = 月存量 × 付费率 × 月均解锁集数 × 单价 × (1 − 抽成)
             · 付费率按月衰减（payerDecay）——老用户比新用户少掏钱
             · 免费集数折算成「白嫖期」，推迟解锁收入的起始月

包月订阅   = 开始试用的比例 × 试用转付费率 × 订阅人群生存率 × 月费 × (1 − 抽成)
             · 试用期按天数折算成小数月（试用 7 天 → 第 1 个月只计 76.7%）
             · 订阅人群生存率 = 大盘生存率 ^ α（订阅者是自选出来的高意愿人群）

混合       = 免费态 → 解锁态 → 订阅态，有状态转移：
             · 该 cohort 人均累计解锁 ≥ 门槛后，每月有 switchRate 比例的解锁用户转向订阅
             · 转向订阅的人里有一部分因预扣费反感直接流失（switchChurn）
             · 转入订阅不再走试用期——他们用累计解锁已经证明了付费意愿
```

留存曲线：锚点之间用对数线性插值**精确穿过每个锚点**，D180 之后按全局幂律 / 指数的斜率外推（哪种 RMSE 小选哪种）。

**主要假设**（完整清单与敏感性见 `docs/ASSUMPTIONS.md`）：

- 用月初值代表整月在册比例（`S_k = r(30(k−1))`），不按月内积分——让手算校验能对上，代价是月内波动被抹平
- 每月新增用户数恒定，不考虑季节性
- 订阅人群粘性指数 `α = 0.85`（经验估计，没有公开基准）
- 混合机制切换摩擦 `switchChurn = 0.35`（经验估计）
- 平台抽成按固定比例，不区分首月 / 续费

## 三个关键产品决策

**一、所有指标统一到 cohort 口径，而不是用「当月总收入 ÷ 当月活跃用户」。**

后者看起来更直观，但它把「刚注册的新用户」和「已经用了半年的老用户」混在一个分母里。一个机制的 LTV 是 30 元还是 12 元，取决于当月新增和存量的比例——而这个比例纯粹由增长快慢决定，和定价机制无关。所以必须锚定「一个新用户从注册起累计贡献多少」，这样它才能直接和 CAC 相除、才能定义「回本月份」。代价是页面上的数字比「月收入」小一个数量级，第一眼看会以为算错了。

**二、留存曲线必须穿过用户拖出来的锚点。**

第一版用一条全局幂律拟合 5 个锚点，结果短剧预设的 D30 实测 9% 被拟合成了 5.6%（误差 40%）。D30 恰好是决定「订阅还是解锁」的核心输入——用户在编辑器里拖到 9%，模型实际拿去算的是 5.6%，结论就是错的。改成锚点间对数线性插值后，所有锚点残差归零；全局幂律 / 指数形式降级为「选形态 + 外推尾部」两个用途。

**三、结论卡的理由从数据里推，不写模板句。**

「订阅更优」这种话没有信息量。结论卡说的是「订阅人群 12 个月内期望付费 8.2 个月、折 ¥143，同样这批人走解锁只贡献 ¥57」——这两个数一个是 `期望付费月数 × 月费 × (1−抽成)`，一个是 `期望解锁集数 × 单价 × (1−抽成)`，都从模型里现算。所以每条曲线的结论都不一样，不是预设答案。推理逻辑在 `lib/model.js` 的 `buildConclusion`。

## 什么失败了，怎么修的

**一、混合机制静默退化成纯解锁。**

第一版跑敏感性扫描，三种机制里混合和解锁的 LTV **完全相等**（小数点后十位都一样）。查下来是两个 bug 叠在一起：

- 门槛判断写错了量纲。我把「整个 cohort 的解锁总数」拿去和门槛比，但那个数的单位是「人数 × 集数」，比门槛大四个数量级——要么所有人第 2 个月就"达标"，要么永远不达标。正确做法是用**单个人均累计解锁集数**。
- `rateAtMonth(curve, 1)` 返回的是 `r(30)` 而不是 `r(0)`。文档里我写的约定是「第 1 个月 = 新用户当月必然在册 = 100%」，代码实现却偏移了一个月，导致所有机制的第 1 个月存量都按 D30 值算。修完后「沉淀 100% 时 S_k ≡ 1」这条手算校验才通过。

这两个都是**不会报错的错**——没有异常、没有 NaN，只是数字悄悄错了。如果当时校验只跑「结果是不是正数」这种检查，就全漏过去了。

**二、曲线不穿过用户给的锚点。**

见上面「三个关键产品决策」第二条。这个坑的性质和上一个一样：模型照常跑、页面照常渲染、结论照常给出，只是**结论建立在一条用户没画过的曲线上**。发现它是因为我把拟合残差打出来看（`results/model-check.json` 里那组「严格幂律锚点 → RMSE ≈ 0」的用例）——残差表一摊开，D30 差 3.4 个百分点就藏不住了。

**三、案例页整页白屏，但同样的计算在 Node 里全过。**

`components/cases.js` 里写成了 `Object.fromEntries([...presets].map(...))`，而 `presets` 是 `data/presets.json` 的**整个对象**（`{ alpha, presets: [...] }`），不是数组。展开一个对象得到的是空数组，于是 `presetById` 是空的，案例去查留存曲线查到 `undefined`，React 渲染时抛异常——整个页面白屏。

讽刺的是我用 Node 单独跑过每个案例的计算，4 个案例全 OK。因为 Node 里我是手动构造的 `retention` 对象，根本没走组件那条查表路径。**校验要和出问题的那条路径跑同一份代码**，否则测了个寂寞。

## 校验

三组校验脚本，产物都在 `results/`，README 里引用的每个数字都能在那里找到。

**1. 手算对照**（`scripts/test-model.mjs` → `results/model-check.json`）

26 条断言全部针对「不看代码、只在纸上算就能得出预期值」的极端情形。例如：

| 场景 | 预期 | 结果 |
|---|---|---|
| 留存恒 100% + 无抽成 + 月费 10 + 全员付费 | 12 月 LTV = 120 | ✓ |
| 同上 + 平台抽成 30% | 12 月 LTV = 42（= 120 × 0.7） | ✓ |
| 同上 + 折现率 10%/月 | 12 月 LTV = 10 × 年金因子 = 74.95 | ✓ |
| 零流失 + 月费 10 + CAC 25 | 回本月份 = 第 3 个月（累计 10/20/30） | ✓ |
| 免费 25 集（= 1 个月白嫖期） | 只有 11 个月有收入，LTV = 33 | ✓ |
| 月费 10 → 20 | 订阅 LTV 精确翻倍 | ✓ |
| 混合机制 `switchRate = 0` | 与纯解锁 LTV 完全相等（状态机退化检查） | ✓ |
| 严格幂律锚点 0.5·d^(−0.5) | 拟合斜率回到 −0.5、RMSE ≈ 0 | ✓ |

**26 / 26 通过。**

**2. 守恒检查**（`scripts/sanity.mjs` → `results/sanity.json`）

让三种机制在「价格设为等价」的参数下跑——单集 ¥1 × 月均 3 集 = 月付 ¥3——看收入是否收敛：

- 等价定价 + 零流失下，**纯解锁与纯订阅的 LTV 一致**（相对差 < 1e-9）✓
- 三种机制在抽成从 0 提到 30% 后，LTV 都**恰好乘以 0.7** ✓
- 逐月收入级联守恒：`第 m 月收入 = 新增用户数 × Σ_{k≤m} revUnit(k)`，三种机制都对得上 ✓
- 量级上界：真实曲线下三种机制的 LTV 都不超过「全员每月满额付费」的上界 ✓
- 折现率 0% → 5% → 10%，LTV 严格递减 ✓

**12 / 12 通过。** 不收敛就说明模型有 bug，修好再提交——这也是上面第一个 bug 的发现方式。

**3. 敏感性扫描**（`scripts/sweep.mjs` → `results/sweep.json`）

对三条预设曲线，各扫五个维度找「最优机制的换手点」。基准参数（CAC ¥8、抽成 30%）下的结果：

| 曲线 | D30 | 单次解锁 LTV | 包月订阅 LTV | 混合 LTV | 当月最优 |
|---|---|---|---|---|---|
| 短剧类 | 9.0% | ¥6.13 | ¥6.29 | **¥7.86** | 混合 |
| 工具类 | 17.0% | ¥7.53 | ¥8.55 | **¥10.10** | 混合 |
| 社交类 | 20.0% | ¥8.30 | ¥10.20 | **¥11.44** | 混合 |

**月费维度的切换边界**——这是全项目最有说服力的一个结果：

| 曲线 | 月费低于此值时 | 月费高于此值时 |
|---|---|---|
| 短剧类（D30 = 9%） | 混合更优 | **¥37.75 起，订阅反超** |
| 工具类（D30 = 17%） | 混合更优 | **¥35.75 起，订阅反超** |
| 社交类（D30 = 20%） | 混合更优 | **¥33.25 起，订阅反超** |

值得注意的规律：**留存越好，切换点越低**。社交类（D30 = 20%）在月费 ¥33.25 就该考虑转订阅，短剧类（D30 = 9%）要等到 ¥37.75——因为留存好的产品，订阅的续费能把长尾接得更久，不需要靠高价来撑起 LTV。

其他维度的切换边界（完整数据见 `results/sweep.json`）：

- **免费集数**：短剧类给到 10 集以上、工具类 8 集以上、社交类 8 集以上时，订阅反超混合——白嫖期太长会把解锁收入饿死
- **订阅转化率**：低于 56%~63% 时混合更稳；转化率足够高时订阅单押更划算
- **切换摩擦**：摩擦超过 58%~71% 时，混合机制会被订阅反超——把用户推去订阅这个动作本身有代价

**D30 留存维度没有切换点**：三种机制里混合一路占优。原因是**混合在数学上是纯解锁的超集**（解锁收入 + 订阅增量），除非切换摩擦大到把增量吃光，否则它不可能低于纯解锁。这是模型的结构性事实，不是 bug——但它也说明「混合更好」这个结论的信息量低于「月费超过 ¥38 就该转订阅」。

## 已知局限与下一步

- **月内按日积分**：目前用月初值代表整月，月内波动被抹平。月内积分更准，但会让所有手算校验对不上——想改的话在 `lib/retention.js` 的 `monthlySurvival` 里换成 `∫ r(t) dt / 30`
- **单一订阅档位**：只有一档月费，没有年费、没有基础版 / 高级版分层。真实订阅制产品往往是多档
- **用户不分层**：全员一条留存曲线，不能按地域 / 获取渠道拆不同留存。真实产品里不同渠道的用户 LTV 能差好几倍
- **新增恒定为常数**：不考虑指数增长、季节性、大促。扫参数时看到的「12 个月累计收入」只是量级参考，不能当财务预测
- **`α` 和 `switchChurn` 缺公开基准**：这两个直接决定订阅和混合的 LTV，但我只能拍到「感觉合理」的值，标在 `docs/ASSUMPTIONS.md` 里待复核
- **`fit: power/exp` 与自动选择**：`data/presets.json` 里标了每条曲线「期望的」形态，但模型是自动按 RMSE 选的。如果某条曲线的拟合形态和标注的不一致，说明锚点值本身有问题——目前三条都一致
- **不做 A/B 实验设计**：只做事后算账，不管怎么分流上线
