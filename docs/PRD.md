# PRD：付费机制模拟器

## 用户

**目标用户**：独立开发者、小型内容应用主、订阅制产品的产品经理。任何在「买断还是订阅」之间纠结的人。

**典型场景**：
- 独立开发者上了一个付费功能，两周后收入平了，不确定该继续单次解锁还是加一档包月
- 小团队做短剧 App,看到某个市场的订阅复购率比解锁高三倍,想说服老板全面切订阅,但老板要看「同一批用户切过去到底能多赚多少」
- PM 被问「这个定价的临界点在哪」,Excel 表已经算不动了

## 问题

收入连续下滑时,团队第一反应往往是加买量。但问题可能不在获客,而在**付费机制**——包月订阅市场的复购率可以比单集解锁市场高三倍多。

最花时间的不是分析,是**说服**：让所有人看到「不同付费机制在同一批用户上会跑出多大的收入差」。Excel 表能算一两组参数,但要扫一遍「月费从 25 到 40、免费集数从 0 到 15」找切换边界,手算就崩了。

## 范围

### 做什么

一个浏览器端的模拟器,四个页面:

1. **留存曲线编辑器**：拖锚点画出 D1/D7/D30/D90/D180,或选预设(短剧/工具/社交三类)
2. **三机制对比**(核心页):输入 CAC、定价、试用天数等参数,算出 12 个月的 ARPU/LTV/回本月份,三条线对比,**附一张结论卡用人话说谁更优、为什么**
3. **敏感性分析**:扫一个参数(如月费 20-50),看三种机制的 LTV 怎么变、**在哪个值上最优机制发生切换**
4. **案例库**:3-4 个合成案例,每个是「留存曲线 + 参数 + 模拟器结论 + 我的点评」

### 不做什么

- **不做广告变现模型**——只算付费,不算 eCPM
- **不做真实支付**——只算数,不对接 Stripe/微信支付
- **不做税费 / 渠道分成的精细计算**——用一个可调的「平台抽成」参数带过(默认 30% 对应应用商店,网页支付可以调到 5%)
- **不做多币种**——统一用人民币符号,实际是无量纲的「货币单位」
- **不做 A/B 实验设计**——只做事后算账,不管怎么分流、怎么上线

## 成功标准

1. **算得对**：`scripts/test-model.mjs` 里 ≥6 组手算值能对上(如「留存恒 100%、无抽成、月费 10 → 12 月 LTV = 120」)
2. **说得清**：README 前三节,一个不懂付费模型的人能看懂这东西干什么、为什么要做、核心假设是什么
3. **能说服人**：结论卡不写「订阅更优」这种模板句,而是「订阅在留存 >40% 时才划算,你 D30 只有 22%,所以解锁更稳」——从数据里推出来的判断
4. **跑得通**：`npm run dev` 能在本地起,`npm run build` 能导出静态站,部署到 GitHub Pages 后四个页面都能点开

## 约束

- Next.js 15 + React 19 + **JavaScript**(不是 TypeScript),沿用姊妹仓库 `creative-eval` 的技术栈
- 图表用 Recharts,不引入 D3(太重)或 Chart.js(画三线对比的代码比 Recharts 啰嗦)
- 所有计算在浏览器端完成,不需要后端、不调 LLM(本项目的数据生成和校验脚本在**开发时**可以用 LLM,但产物是静态的 JSON,**用户**用模拟器时不调 API)
- 合成数据必须标明「合成」并写清生成规则,不许把实习公司的内部数据或内部留存曲线拿来当案例

## 版本 1.0 不包含(留给 v2)

- 动态增长率(如「每月新增不是常数,而是指数增长」)——v1 假设每月新增恒定
- 多档订阅(如基础版 15 / 高级版 30)——v1 只有一档月费
- 年费——v1 只有月订阅
- 用户分层(如按地域 / 年龄段拆不同留存)——v1 全员一条曲线
- 从后台导出真实数据——v1 只有手动输入和预设

---

**核心取舍**：宁可把单一场景算透(内容 / 订阅类产品的三种付费机制对比),也不要做成一个大而全、什么都能配、每个维度都浅尝辄止的「通用商业模型沙盒」。后者学习成本高、没人用。
